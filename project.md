### Контекст и пользователи

`video_managment` является отдельным сервисом учебной видеохостинговой платформы. В границы данной работы входит только этот сервис; остальные компоненты платформы рассматриваются как внешние системы в части их взаимодействия с ним.

Основной пользовательский сценарий - загрузка видео авторизованным пользователем. Сервис получает идентификатор пользователя из JWT, создает метаданные видео через `video_metadata`, создает запись объекта хранения, возвращает временный presigned URL для прямой загрузки файла в Garage, а после подтверждения загрузки проверяет наличие объекта, переводит его из `PENDING_UPLOAD` в `UPLOADED` и публикует событие `video.uploaded` в Kafka.

Внутренние сервисы платформы также могут использовать внутренний API для получения временной ссылки на чтение загруженного видео.

Для пользователей и платформы важны:
- корректная аутентификация и определение владельца видео;
- недоступность пользовательских операций над чужими объектами;
- целостность связи между видео, владельцем и объектом в хранилище;
- ограниченность срока и области действия presigned URL;
- корректность состояния загрузки и события `video.uploaded`.

Решение о готовности выпуска `v1.0.1` принимает команда из двух участников на основании результатов проверок и известных ограничений.

### Компоненты, взаимодействия и границы доверия

| Компонент | Назначение | Существенная граница |
|---|---|---|
| `VideoStorageController` | Пользовательские операции загрузки и получения данных об объекте | Внешний пользователь -> сервис |
| Spring Security / JWT | Аутентификация и получение пользователя из `sub` JWT | JWT -> доверенный `ownerId` |
| `InternalVideoStorageController` | Получение временной ссылки на чтение видео внутренними сервисами | Внутренний сервис -> внутренний API |
| `VideoStorageService` | Основная бизнес-логика и проверка владельца/статуса | Координация данных между компонентами |
| PostgreSQL | Связь `videoId`, `ownerId`, `objectKey` и статуса | Приложение -> БД |
| Garage | Хранение видео и работа через presigned URL | Приложение/клиент -> объектное хранилище |
| `video_metadata` | Создание метаданных и получение `videoId` | Межсервисный REST |
| Kafka | Передача `video.uploaded` дальнейшим обработчикам | Сервис -> асинхронный pipeline |

Основной поток загрузки:

```text
Пользователь + JWT
        |
        v
video_managment
   |        |
   |        +----> video_metadata
   |
   +-------------> PostgreSQL
   |
   +-------------> Garage -> presigned PUT URL -> Пользователь -> Garage
```

После подтверждения загрузки:

```text
Пользователь -> video_managment -> проверка Garage
                              -> PostgreSQL: UPLOADED
                              -> Kafka: video.uploaded
```

- `src/main/java/.../services/VideoStorageService.java`
- `src/main/java/.../configs/SecurityConfig.java`

Открытый вопрос для дальнейшего анализа: каким механизмом в целевом окружении ограничивается доступ к внутреннему API `video_managment`.

### Активы и существенные риски

- **Актив:** исходные видеофайлы пользователей.  
  **Что может произойти:** неразрешенное чтение или изменение объекта.  
  **Почему существенно:** нарушаются конфиденциальность и целостность пользовательского контента.

- **Актив:** связь `videoId -> ownerId -> objectKey`.  
  **Что может произойти:** операция выполняется над объектом другого пользователя.  
  **Почему существенно:** эта связь используется для разграничения доступа и выбора физического объекта.

- **Актив:** presigned URL.  
  **Что может произойти:** ссылка попадает к другому субъекту или действует дольше/шире необходимого.  
  **Почему существенно:** после выдачи ссылки обращение к Garage выполняется напрямую, без повторной проверки REST API сервиса.

- **Актив:** состояние загрузки и событие `video.uploaded`.  
  **Что может произойти:** обработка запускается для некорректного объекта либо корректно загруженное видео не передается дальше.  
  **Почему существенно:** событие связывает загрузку с последующим processing pipeline.

## 2. Методологическая основа

### Требования проекта к методологической основе

Методологическая основа должна:

- охватывать безопасную разработку на протяжении всего жизненного цикла, а не только тестирование;
- быть применимой к небольшому backend-сервису и команде из двух человек без создания формальных ролей и процессов, которых в проекте нет;
- позволять выбирать практики по риску и адаптировать их к выпуску `v1.0.1`;
- связывать действия команды с проверяемыми результатами: изменениями кода, review, тестами, настройками и решением о выпуске;
- допускать использование отдельного технического источника для конкретизации требований к безопасности web/API-компонентов.

### Сравнение кандидатов

| Рамка | Для чего предназначена | Применимость к `video_managment` | Что пришлось бы адаптировать | Решение |
|---|---|---|---|---|
| **NIST SSDF 1.1 (NIST SP 800-218)** | Набор практик безопасной разработки, встраиваемых в существующий SDLC | Хорошо соответствует задаче: охватывает подготовку, разработку, проверки перед выпуском и реакцию на найденные проблемы | Организационные формулировки и роли необходимо уменьшить до масштаба команды из двух человек | **Основная рамка** |
| **ГОСТ Р 56939-2024** | Требования к процессам разработки безопасного ПО | Охватывает жизненный цикл и подходит по предметной области | Для небольшого учебного сервиса значительная часть организационных требований была бы избыточна | Не берем |
| **OWASP SAMM 2** | Модель оценки и последовательного развития зрелости практик безопасности | Может быть полезна для оценки состояния и построения программы улучшений | Полноценная оценка зрелости организации шире границ одного сервиса и одного patch-выпуска | Не берем |
| **OWASP ASVS 5.0.0** | Каталог проверяемых требований безопасности web-приложений и API | Хорошо подходит для уточнения технических требований к аутентификации, авторизации, API и защите данных | Нужно выбирать только требования, относящиеся к нашему сервису; ASVS не задает полный Secure SDLC | **Дополнительный источник** |

### Выбранная основная рамка

Основной рамкой проекта выбран **NIST Secure Software Development Framework (SSDF) Version 1.1, NIST SP 800-218**.

SSDF выбран потому, что он задает набор практик, которые можно встроить в существующий жизненный цикл разработки, не требуя перехода на отдельную методологию разработки. Для `video_managment` это позволяет связать уже определенные свойства и риски продукта с требованиями к изменению кода, проверкам и решению о выпуске `v1.0.1`. Рамка также допускает адаптацию под размер и ресурсы команды. В нашем случае ее организационные роли и процессы будут сведены к действиям двух участников.

### Дополнительный источник

В качестве дополнительного технического источника выбран **OWASP ASVS 5.0.0**.

ASVS используется для конкретизации отдельных технических требований и проверок, связанных с web/API-частью `video_managment`, прежде всего:

- аутентификацией и обработкой JWT;
- авторизацией операций над объектами;
- внутренним REST API;
- обработкой входных данных;
- защитой данных и взаимодействием с внешними компонентами.

ASVS не используется как основная рамка, поскольку он определяет требования к проверке безопасности приложения, но не организует полный процесс Secure SDLC и принятия решения о выпуске.

### Почему остальные варианты не выбраны

**ГОСТ Р 56939-2024** не выбран основной рамкой, поскольку для команды из двух человек и одного небольшого backend-сервиса потребовал бы существенного упрощения организационной части. Его применение не дает достаточного преимущества перед более компактным SSDF в пределах учебного проекта.

**OWASP SAMM 2** не выбран основной рамкой, поскольку ориентирован прежде всего на оценку и развитие зрелости практик безопасности организации. Наш проект ограничен одним сервисом, одним baseline и одним планируемым выпуском, поэтому полноценная maturity assessment создала бы лишний объем работы и не была бы напрямую связана с целью проекта.

### Адаптация NIST SSDF 1.1 к проекту

Для `video_managment` выбраны семь практик SSDF 1.1. Они применяются не как полный корпоративный процесс, а как небольшой набор проверяемых правил для команды из двух человек и выпуска `v1.0.1`.

#### PO.1 - Define Security Requirements for Software Development

**Применимость:** частично.

**Почему относится к проекту:** в паспорте уже выделены критичные для сервиса свойства: аутентификация по JWT, проверка владельца объекта, работа с presigned URL, внутренний API и корректность перехода `PENDING_UPLOAD -> UPLOADED`.

**Действие:** перед реализацией изменения определить, какие из этих свойств и границ доверия оно затрагивает, и зафиксировать применимые требования безопасности.

**Ответственность:** автор изменения формулирует требования; второй участник проверяет их полноту и связь с паспортом.

**Результат:** краткая запись применимых требований в описании изменения, `project.md` или связанном issue/PR.

**Проверка выполнения:** для значимого изменения можно показать, какое защищаемое свойство было затронуто и каким требованием оно ограничено.

**Упрощение:** не создается отдельная корпоративная политика требований; используется компактный перечень требований конкретного сервиса.

#### PO.2 - Implement Roles and Responsibilities

**Применимость:** частично.

**Почему относится к проекту:** безопасные изменения и решение о выпуске должны иметь исполнителя и второй взгляд, однако команда состоит только из двух человек.

**Действие:** автор изменения выполняет реализацию и первичную проверку, второй участник проверяет значимые изменения и результаты проверок. Для следующей задачи роли могут меняться.

**Ответственность:** оба участника; автор не считается независимым проверяющим собственного изменения.

**Результат:** review, комментарий или иная фиксируемая отметка второго участника для значимых изменений.

**Проверка выполнения:** по истории изменения можно определить автора и факт проверки другим участником.

**Упрощение:** не вводятся отдельные роли security engineer, auditor или security champion; обучение и корпоративная матрица ролей в границы проекта не входят.

#### PO.4 - Define and Use Criteria for Software Security Checks

**Применимость:** полностью в масштабе выбранного выпуска.

**Почему относится к проекту:** одного факта успешной сборки недостаточно для утверждения, что свойства безопасности `video_managment` сохранены.

**Действие:** для каждого значимого изменения заранее определить ожидаемый результат проверки. Перед выпуском сопоставить полученные результаты с затронутыми требованиями безопасности и открытыми вопросами.

**Ответственность:** автор получает результат проверки; второй участник сверяет его с ожидаемым критерием.

**Результат:** воспроизводимый результат теста или проверки, связанный с конкретной версией кода.

**Проверка выполнения:** по результату можно однозначно определить, выполнен критерий или нет; отсутствие необходимого результата не считается успешной проверкой.

**Упрощение:** формальные KPI/KRI и корпоративные security gates не вводятся; используются критерии, относящиеся непосредственно к `v1.0.1`.

#### PW.1 - Design Software to Meet Security Requirements and Mitigate Security Risks

**Применимость:** частично.

**Почему относится к проекту:** сервис содержит несколько явных границ доверия и активов: JWT, связь `videoId -> ownerId -> objectKey`, presigned URL, внутренний API и событие `video.uploaded`.

**Действие:** если изменение затрагивает один из этих элементов, до реализации определить затронутый актив или границу доверия, возможное последствие и способ снизить риск на уровне дизайна или реализации.

**Ответственность:** автор изменения выполняет анализ; второй участник проверяет связь решения с риском.

**Результат:** краткая запись `риск -> решение` в описании изменения или `project.md`.

**Проверка выполнения:** из записи должно быть понятно, почему выбранное решение относится к указанному риску и что именно оно должно защищать.

**Упрощение:** полноценная формальная threat model для всей видеохостинговой платформы не строится; анализ ограничен изменяемой частью `video_managment`.

#### PW.7 - Review and/or Analyze Human-Readable Code

**Применимость:** полностью для значимых изменений исходного кода.

**Почему относится к проекту:** ошибки в проверке владельца, обработке JWT, генерации presigned URL или внутреннем API могут непосредственно нарушить свойства, указанные в паспорте.

**Действие:** изменения, затрагивающие безопасность или границы доверия, до включения в выпуск просматриваются вторым участником с фокусом на соответствующие требования и риски.

**Ответственность:** автор подготавливает изменение; второй участник выполняет review.

**Результат:** зафиксированный результат review и, при наличии замечаний, внесенные исправления.

**Проверка выполнения:** для значимого изменения существует второй взгляд и можно установить, какие замечания были приняты или почему изменение признано допустимым.

**Упрощение:** обязательным минимумом является второй взгляд на значимые изменения исходного кода. Автоматизированный статический анализ используется только там, где он дает проверяемый результат для конкретного требования или риска; отдельный корпоративный процесс SAST не вводится.

#### PW.8 - Test Executable Code to Identify Vulnerabilities and Verify Compliance with Security Requirements

**Применимость:** полностью.

**Почему относится к проекту:** ключевые свойства безопасности `video_managment` проверяемы на работающем приложении: отклонение запроса без корректного JWT, запрет операций над чужим объектом, корректная обработка состояний загрузки и поведение API на границах доверия.

**Действие:** перед выпуском запускать автоматизированные тесты и воспроизводимые проверки работающего сервиса для всех требований безопасности, затронутых изменением. Для API-поведения используются интеграционные тесты или повторяемые HTTP-запросы с заранее определенным ожидаемым результатом.

**Ответственность:** автор изменения подготавливает и выполняет необходимые проверки; второй участник проверяет, что они действительно подтверждают заявленное свойство и относятся к проверяемой версии.

**Результат:** автоматизированный тест либо сохраненный воспроизводимый сценарий проверки с входными данными, ожидаемым и фактическим результатом.

**Проверка выполнения:** проверка повторно выполняется на той же версии; результат должен однозначно показывать выполнение или нарушение сформулированного требования.

**Упрощение:** область проверки ограничена `video_managment` и его непосредственными интерфейсами. Не требуется тестирование всей видеохостинговой платформы, production-среды или проведение полного внешнего penetration test, если это не связано с конкретным риском выбранного сервиса.

#### RV.2 - Assess, Prioritize, and Remediate Vulnerabilities

**Применимость:** частично.

**Почему относится к проекту:** обнаруженная проблема должна приводить не только к исправлению кода, но и к понятному решению о приоритете и влиянии на выпуск.

**Действие:** для подтвержденной проблемы зафиксировать затронутое свойство, область влияния, приоритет и ближайшее действие: исправить, дополнительно исследовать или вынести на отдельное решение перед выпуском.

**Ответственность:** обнаруживший проблему описывает ее; второй участник проверяет обоснование приоритета и результат исправления.

**Результат:** issue, запись в `project.md` или другой проверяемый след с состоянием проблемы и ссылкой на исправление/проверку.

**Проверка выполнения:** перед выпуском можно определить статус всех существенных обнаруженных проблем и основание для их закрытия либо дальнейшего рассмотрения.

**Упрощение:** круглосуточный vulnerability management и отдельная служба реагирования не моделируются; правило применяется к проблемам, обнаруженным в рамках данного проекта и выпуска.


### Использование OWASP ASVS 5.0.0

OWASP ASVS 5.0.0 используется как дополнительный технический источник для конкретизации отдельных требований, определенных в рамках NIST SSDF 1.1.

ASVS не формирует отдельный процесс разработки и не используется как вторая основная рамка. Его требования применяются только там, где необходимо уточнить конкретное проверяемое свойство `video_managment`.

Связь с адаптированными практиками SSDF:

| Практика SSDF | Роль ASVS в проекте |
|---|---|
| **PO.1 - Security Requirements** | ASVS используется как источник конкретных требований к аутентификации, авторизации, API и обработке данных |
| **PO.4 - Security Check Criteria** | Требования ASVS помогают определить ожидаемый результат отдельных security-проверок |
| **PW.1 - Secure Design** | ASVS используется для уточнения технических свойств при изменениях JWT, внутреннего API, доступа к объектам и обработки данных |
| **PW.7 - Code Review** | При review изменений, затрагивающих безопасность, применимые требования ASVS используются как ориентир проверки |
| **PW.8 - Executable Code Testing** | На основе применимых требований ASVS формируются поведенческие проверки работающего сервиса |

Для `video_managment` в первую очередь рассматриваются области ASVS, связанные с:

- аутентификацией и обработкой JWT;
- авторизацией операций над пользовательскими объектами;
- безопасностью API и внутренних endpoint;
- валидацией и обработкой входных данных;
- защитой данных;
- безопасным взаимодействием с внешними компонентами.

Конкретные требования ASVS и их идентификаторы определяются при анализе baseline `v1.0.0` для тех свойств, которым требуется дополнительная техническая проверка. Поэтому мы не заявляем полное соответствие ASVS 5.0.0 или какому-либо его уровню.

### Итоговый методологический профиль

Для выпуска `v1.0.1` мы используем следующую цепочку:

```text
определить затронутое требование и риск
        ->
реализовать изменение
        ->
получить второй взгляд на значимое изменение
        ->
выполнить обычные и необходимые проверки свойства
        ->
сохранить воспроизводимый результат
        ->
разобрать обнаруженные проблемы
        ->
использовать результаты как основание для решения о выпуске
```

### Что сознательно не включено

NIST SSDF 1.1 используется выборочно и адаптируется под небольшой backend-сервис `video_managment`, один планируемый выпуск `v1.0.1` и команду из двух человек. 

В проект сознательно не включаются элементы рамки, рассчитанные на более крупную организационную структуру. Не вводятся отдельные подразделения или специализированные роли безопасности, многоуровневые процедуры согласования, корпоративные программы обучения и отдельные процессы управления полномочиями сотрудников. Выполнение, проверка и принятие решений распределяются между двумя участниками команды. Также не создается отдельная корпоративная среда безопасной разработки и полноценная система управления release-артефактами. Исходный код, история изменений и версии продукта фиксируются средствами Git, а результаты проверок сохраняются в репозитории или связанных с ним материалах. Управление поставщиками и сторонним программным обеспечением рассматривается только в части зависимостей самого `video_managment`. Полноценный организационный процесс управления цепочкой поставки ПО выходит за границы проекта. Не моделируется и отдельный постоянный процесс мониторинга уязвимостей после выпуска. В рамках проекта рассматриваются проблемы, обнаруженные при анализе и проверке `video_managment`, их приоритизация, исправление и повторная проверка. 

Таким образом, из SSDF сохраняются те практики, которые непосредственно влияют на требования безопасности, разработку, review, проверку исполняемого кода, обработку обнаруженных проблем и принятие решения о выпуске.

### Вопросы для анализа текущего состояния

При анализе baseline `v1.0.0` необходимо проверить:

- есть ли в доступной истории свидетельства второго взгляда на значимые изменения;
- какие автоматизированные тесты реально существуют и какие свойства они проверяют;
- есть ли сохраненные результаты проверок, связанные с конкретной версией;
- каким образом фактически ограничивается доступ к внутреннему API;
- есть ли наблюдаемый порядок подготовки и принятия решения о выпуске;
- как в доступной истории фиксировались и исправлялись обнаруженные проблемы.

### Предварительные решения

Общая логика процесса безопасной разработки уже определена, однако некоторые детали остаются предварительными до анализа baseline `v1.0.0`.

Пока не выбран окончательный набор конкретных требований OWASP ASVS 5.0.0. Области его применения уже определены - аутентификация и JWT, авторизация, внутренний API, обработка входных данных, защита данных и взаимодействие с внешними компонентами. Конкретные требования ASVS будут выбраны для тех свойств, где анализ текущего состояния покажет необходимость дополнительной технической конкретизации.

Предварительным остается точный критерий значимого изменения. Уже принято правило, что изменения, влияющие на безопасность или границы доверия, должны получать второй взгляд, однако точный перечень таких изменений будет уточнен по фактической структуре и истории сервиса.

Также не фиксируется один универсальный способ технической проверки. Для каждого требования должен существовать воспроизводимый результат, но конкретный метод выбирается по свойству: автоматизированный тест, интеграционный тест, HTTP-сценарий, анализ зависимостей, статический анализ или другой подход.

Форма хранения свидетельств также окончательно не зафиксирована. Результаты должны быть связаны с конкретной версией продукта, но в зависимости от типа проверки это могут быть тесты в репозитории, файлы в `evidence/`, вывод команд, HTTP-ответы или ссылки на commit и review.

Предварительным остается и решение о необходимости изменения защиты внутреннего API. Сначала необходимо определить фактический механизм доступа в baseline. Только если будет подтвержден существенный разрыв, будет выбран конкретный способ его устранения и проверки.

Окончательный набор критериев готовности выпуска `v1.0.1` также будет сформирован после анализа текущего состояния. Уже установлено общее правило: для затронутых значимых свойств должны существовать необходимые результаты проверок, а существенные обнаруженные проблемы должны быть исправлены либо иметь явно зафиксированное решение до выпуска.
